# Synthetic Validation Explained: Data, Process, and Results

---

## What Was the Synthetic Validation?

A pre-registered study to test whether a PSI threshold (specifically T=1.8%) could predict latency degradation. It used **synthetic data** (train.csv, test.csv, validation.csv) generated by a simulator to validate the threshold.

**Result**: The threshold appeared to work. This result was **later retracted** as invalid because the data was co-generated.

---

## The Validation Process

### Step 1: Define Baseline

From **calibration data** (calm sessions):
- Baseline latency **B = 60.34 ms** (median p99 latency during normal operation)
- Breach threshold = **2*B = 120.68 ms** (latency degradation threshold)
- When latency_ms > 120.68, mark as a "breach" event

### Step 2: Label the Data

**Breach label** = 1 when latency > 120.68 ms for 2+ consecutive bins, else 0

**Result on test data**:
- Total test rows: ~5,000
- Breach rows: 18 events detected
- Calm rows: ~4,982 rows (no breaches)
- Test duration: 28.8 hours

### Step 3: Test Thresholds (Sweep)

For each threshold **T** and consecutive-bins requirement **k**:

| T (%) | k | Rule |
|-------|---|------|
| 0.5 | 1 | Alert when psi_some_avg10 > 0.5% for ≥1 consecutive bin |
| 0.5 | 3 | Alert when psi_some_avg10 > 0.5% for ≥3 consecutive bins |
| 1.0 | 1 | Alert when psi_some_avg10 > 1.0% for ≥1 consecutive bin |
| 1.8 | 1 | Alert when psi_some_avg10 > 1.8% for ≥1 consecutive bin |
| ... | ... | ... |
| 9.0 | 3 | Alert when psi_some_avg10 > 9.0% for ≥3 consecutive bins |

### Step 4: Compute Metrics for Each Threshold

For each (T, k) pair, calculate:

| Metric | Formula | Meaning |
|--------|---------|---------|
| **Recall** | (Detected Breaches) / (Total Breaches) | % of real breaches we caught |
| **FA/hr** | (False Alarms) / (Calm Hours) | False alerts per hour on calm data |
| **Precision** | (True Alerts) / (Total Alerts) | % of alerts that are real breaches |
| **Lead time** | Time from alert to actual breach | How early we warned |

## Results: T=1.8% k=1 (The Project Threshold)

### Synthetic Data Result (Now Known to Be Invalid)

```
T = 1.8%
k = 1 (alert on first detection)

Test metrics:
  Recall:              1.0000 (100% — caught all 18 breaches)
  FA/hr:               5.69 per hour (5.69 false alerts per hour)
  Precision:           0.099 (10% of alerts were real breaches)
  Lead time (median):  -60s (detected 60 seconds AFTER breach started)
  n_alerts:            182 total alerts in 28.8 hours
  false_alarms_total:  164 false alerts
  
Verdict: NOT_SUPPORTED
Reason: FA/hr = 5.69 exceeds limit of 2.0/hr
         Recall is high (100%), but too many false alarms
```

### Trade-off Across All Thresholds (Synthetic)

| T | k | Recall | FA/hr | Viable? | Status |
|---|---|--------|-------|---------|--------|
| 0.5 | 1 | 100% | 7.40 | ✗ | Too many FAs |
| 1.0 | 1 | 100% | 6.60 | ✗ | Too many FAs |
| 1.8 | 1 | 100% | 5.69 | ✗ | Too many FAs |
| 2.5 | 1 | 100% | 5.00 | ✗ | Still > 2.0 |
| 3.0 | 1 | 94% | 4.51 | ✗ | Still > 2.0 |
| 6.0 | 1 | 0% | 1.53 | ✗ | No recalls |
| 9.0 | 1 | 0% | 0.0 | ✗ | No alerts at all |

**Finding**: Even in synthetic data, **no threshold satisfied both recall ≥ 60% AND FA/hr ≤ 2.0**.

## Why This Result Was Invalid

### Proof 1: Signal-Outcome Correlation = 0.9996

From the test data:
```
pearsonr(psi_some_avg10, latency_ms) = 0.9996
```

This correlation is **impossibly high** for real measurements:
- Real independent systems: correlation 0.1–0.7
- Even highly correlated: rarely > 0.95
- **0.9996 = co-generation**

### Proof 2: Flat Lag Profile

Testing correlation at different time lags:

```
Lag (seconds):  -60   -40   -20    0   +20   +40   +60
Correlation:   0.99  0.99  0.99  1.00  0.99  0.99  0.99
```

**What this means**:
- Real predictive signal: Would peak at negative lag (e.g., lag -10s means signal leads outcome)
- Real reactive signal: Would peak at positive lag (e.g., lag +20s means signal follows outcome)
- **This data: Flat across all lags** = Not timing-dependent, just co-generated

### Proof 3: Data Generator Source Code

From `generate_server_data.py`:

```python
# Line 95+
latency_ms = 45 + 28*load + 75*psi_some_avg10 + noise
psi_some_avg10 = np.clip(pressure*0.75 + noise, ...)
pressure = f(load)  # Both derived from same load
```

**Both latency and PSI depend on the same `load` variable.**

Testing a threshold on data where both variables come from the same formula will always show high correlation and successful predictions. This validates the generator, not the system.

## The Critical Failure of Synthetic Validation

### Why It Looked Good

✓ 100% recall (caught all breaches)  
✓ 0.9998 AUC (perfect separation)  
✓ Perfect methodology (frozen rules, pre-registration, chance test)  

### Why It Was Worthless

✗ Data is co-generated (correlation 0.9996)  
✗ Real infrastructure may have correlation 0.3–0.6  
✗ Any threshold will work on co-generated data  
✗ Threshold may fail completely in production  

---

## What Real Data Shows (Live Host Sessions)

When the same threshold was tested on real measurements from live infrastructure:

| Metric | Synthetic CSV | Real Live Data |
|--------|---------------|----------------|
| Signal-latency correlation | 0.9996 | 0.456 |
| AUC | 0.9998 | 0.801 |
| T=1.8% k=1 recall (test) | 100% | **0%** |
| Viable thresholds found | 12 pairs | **0 pairs** |

**Verdict**: Synthetic showed 100% recall; real data showed 0% recall. The signal doesn't work on real infrastructure.

---

## Why Synthetic Validation Failed

### The Fundamental Error

Testing a threshold on synthetic data that was **generated to have that property** is circular logic:

```
Signal(t) = f(load, noise)
Outcome(t) = g(load, noise)

Correlation(Signal, Outcome) = 1.0 (by construction)
```

**Testing the threshold on this data proves nothing about real infrastructure.**

### The Lesson

- ✗ Never validate thresholds on co-generated data
- ✗ Never use simulation-based validation for production alerting
- ✓ Always validate on real, independent measurements
- ✓ Always separate calibration and test data
- ✓ Always check for correlation flattening across time lags

## Conclusion

The synthetic validation **appeared to show** that T=1.8% could work with careful tuning (high recall, but too many false alarms).

However, this was an **illusion created by co-generated data**.

Real measurements revealed the **truth**: The signal simply doesn't predict latency degradation on this infrastructure. Correlation is weak (0.456), and no threshold can separate breaches from normal operation.

**Lesson**: Rigorous pre-registered methodology cannot overcome bad data. Always validate on real measurements, not synthetic generators.
