PART 1: THE PROBLEM WE'RE SOLVING
═══════════════════════════════════════════════════════════════════════════════

WHAT IS I/O PRESSURE?
─────────────────────
Your computer has:
  ├─ CPU (brain) - processes information
  ├─ Memory (RAM) - fast temporary storage
  └─ Disk - slow permanent storage

When programs need to read/write files VERY QUICKLY:
  "CPU: Hey disk, give me 1000 files!"
  "Disk: Wait wait wait... I'm overwhelmed!"
  
This "overwhelm" is I/O PRESSURE. It's measured as PSI (Pressure Stall Information).

WHAT DOES HIGH PRESSURE MEAN?
─────────────────────────────
High I/O pressure = Programs are waiting for disk
  ├─ Website loads slowly
  ├─ Database queries hang
  └─ Users get frustrated ❌

Low I/O pressure = Disk is fast enough
  └─ Everything works smoothly ✅


PART 2: WHY PREDICT SPIKES?
═══════════════════════════════════════════════════════════════════════════════

If we can PREDICT when I/O pressure will spike:

BEFORE (Reactive):
  1. Spike happens → Website slow
  2. Users complain → We fix it
  3. Damage already done ❌

AFTER (Predictive):
  1. We predict spike will happen
  2. Move work to another server BEFORE spike
  3. User never notices ✅

Real-world example:
  "Hey, I notice the cache disk is getting lots of reads.
   A spike is coming in the next 10 seconds. Let me move
   the load to server B. No disruption!"

PART 5: WHAT THE MODEL ACTUALLY DOES
═══════════════════════════════════════════════════════════════════════════════

INPUT: Last 30 seconds of I/O pressure readings

Example:
  Time 0s:  PSI = 0.5%
  Time 1s:  PSI = 1.2%
  Time 2s:  PSI = 2.1%
  Time 3s:  PSI = 3.5%
  ...
  Time 30s: PSI = 25.1%  ← Suddenly high!
  
MODEL ANALYSIS:
───────────────
"Let me look at this sequence:
 
 0.5 → 1.2 → 2.1 → 3.5 → ... → 25.1
 
 It was rising slowly, then JUMPED suddenly!
 This looks like a spike forming!
 
 Based on patterns I learned:
 - Spikes usually grow slowly, then jump
 - After a jump, more spike is coming
 - I predict next reading will be: HIGH PSI
 
 Prediction: SPIKE! 🚨
 Confidence: 85%"

OUTPUT: Prediction + Confidence
  ├─ Will next reading be a spike? YES/NO
  ├─ How confident are we? 0-100%
  └─ Takes about 10 milliseconds

This happens every 20 seconds, all day long.


PART 6: HOW WE MEASURE SUCCESS
═══════════════════════════════════════════════════════════════════════════════

THREE MAIN METRICS:
───────────────────

1️⃣ PRECISION
   Question: "When we predict SPIKE, how often are we right?"
   
   Example:
     Model made 100 spike predictions
     Of those 100, 75 were actually spikes
     Of those 100, 25 were false alarms
     
     Precision = 75%
     Translation: "3 out of 4 alerts are real"
   
   Why it matters:
     High precision = Few false alarms = Don't waste resources


2️⃣ RECALL
   Question: "When spikes actually happen, do we catch them?"
   
   Example:
     100 real spikes occurred
     Model detected 88 of them
     Model missed 12 of them
     
     Recall = 88%
     Translation: "Catch 9 out of 10 spikes"
   
   Why it matters:
     High recall = Don't miss spikes = Users don't experience outages


3️⃣ F1-SCORE
   Question: "Overall, how good is the model?"
   
   Formula: Balance between precision and recall
   
   Example:
     Precision = 75%
     Recall = 88%
     F1 = 81%
     
     Translation: "Pretty good, not perfect"


EXPECTED RESULTS:
─────────────────
Training Set (Sessions 1-2):
  ├─ Precision: ~90% (model tuned to these patterns)
  ├─ Recall: ~92% (catches most spikes)
  └─ F1-Score: ~91%

Test Set (Sessions 3-5):
  ├─ Precision: ~75% (some false alarms on new patterns)
  ├─ Recall: ~88% (still catches most spikes)
  └─ F1-Score: ~81%

Translation:
  "Model learned well on easy patterns (~91%).
   On hard patterns it hasn't seen, it still works (~81%).
   This is realistic and trustworthy!"
